## Existing severity machinery

`packages/core/lib/admin/activity-severity.ts` (287 lines) is the W19 severity source of truth. What it provides today:

- **Levels — four, not five:** `failure` (red), `attention` (amber), `notice` (muted/neutral — deliberately *not* the blue `--adm-info` token), `ok` (green check, or a neutral dot for "not started"/"skipped"). Ranked worst-first via `SEVERITY_RANK`/`worstSeverity()`.
- **Mapping functions, with signatures:**
  - `severityTone(severity: Severity): 'danger' | 'warning' | 'neutral' | 'success'` — the only place `Severity` becomes a design tone.
  - `classifyWarning(warning: string): ClassifiedWarning` — prefix-matches a `WARNING_RULES` table (7 known prefixes + a default-to-`notice` fallback) to `{ severity, label, raw }`.
  - `isFatalNodeError(error: string): boolean` — substring-matches against `FATAL_ERROR_CODES` (4 codes: `model_error`, `output_validation_failed`, `schema_validation_failed`, `node_timeout`).
  - `classifyToolCall(call: { status?, errorCode? }): Severity` — collapses everything that isn't `'success'` to `notice` (a capped/denied tool call is never louder than notice).
  - `classifyNode(node: NodeSignals): Severity` — the per-node reducer: `failed` status or a fatal error string → `failure`; `blocked` → `attention`; `skipped` → `ok`; otherwise the worst of its warnings, capped so a *completed* node can never read `failure`.
  - `classifyToolResult(signals: ToolResultSignals): ClassifiedToolResult` — the screenshot-defect fix itself: parses a tool's (possibly nested/MCP-wrapped) JSON body via `bodyOf()`, checks a fatal-code list first (outranks everything), then a `GATE_CODES`/`GATE_PHRASES` list to detect a held gate → `attention` with "…is waiting on you" copy, else `failure`.
  - `toolTitle(tool: string)` — 5 known tool names get human titles; everything else is `snake_case` → `snake case`.
  - `DENIED_SEVERITY = 'notice'` — a human declining a proposed write is not an error.
- **Test coverage** (`activity-severity.test.ts`, 239 lines, ~24 `it()` blocks): the screenshot defect itself (readiness `no_go`, missing human approver, real breakage still red, snake_case never shown, unparseable body doesn't default to "fine"); the always-firing production warnings staying quiet; skip-carries-no-severity; the two warnings that do earn amber; unrecognised-warning defaults to quiet without hiding raw text; node failure only on real death; a warning can't talk a completed node into red; the fatal-code allowlist; tool-call capping treated as routine; `worstSeverity` reduction; tone mapping; the fatal-code-outranks-gate-word precedence (twice, including a bridge-crash case); non-flat error body shapes (MCP envelope, nested envelope, bare sentence, self-referential-shape guard); a fatal error under an unexpected status string.

**Distance from D4, and the extension-vs-new-module question:**

The module is well-built and well-tested for what it does, but it is a **4-level system being asked to become a 5-level one**, and the gap is not cosmetic:

- `failure` needs to split into **Error** (recoverable — retry exists) and **Blocked** (hard stop). The module currently has no signal for "is a retry offered" — that lives in the UI layer (`RequestActivity.tsx`'s `onRetry`/`recovery` prop), not in `activity-severity.ts`. Making this split correctly needs either (a) a new field on `NodeSignals`/`ClassifiedToolResult` the callers populate with retry-availability, or (b) moving the Error/Blocked decision entirely into the presentation layer that already knows about retry affordances — a design decision, not a mechanical rename.
- `notice` needs to become **Info**, and today it is deliberately muted-gray rather than the blue `--adm-info` token that already exists and is used elsewhere (running/queued/draft states). Renaming the tone is trivial; deciding whether "notice" (handled, quiet) and "info" (FYI, visible) are actually the same concept is not — the current design intentionally *demotes* notice below visual parity with other statuses, which D4's 5-level table does not obviously ask for.
- `ok` already splits itself informally into "done" (green check) vs. "skipped"/"not started" (neutral dot) at the UI layer (`RequestActivity.tsx:200-207`, `NodeGlyph`), which is closer to D4's Info/Success split than the type system currently admits — this part translates cleanly.
- The module's scope is **run/node/tool-call activity only**. It has no jurisdiction over the four other severity vocabularies this sweep found — `request-logic.ts`'s `requestStatusTone`, `editorial-state.ts`'s `EDITORIAL_STATE_PRESENTATION`, `library-logic.ts`'s `rowStatus`, `admin/logic.ts`'s generic `statusTone`, and `AdminUsers.tsx`'s `statusToneFor` — each an independent switch statement mapping its own status vocabulary to a tone, none aware of the others (Table C's published/not-live conflict is a direct consequence).

**Verdict:** D4 can be implemented as an **extension of `activity-severity.ts`** for the run/node/tool-call surface specifically (add the Error/Blocked split to `Severity`, retarget `notice`→Info's actual token, thread a "recoverable" signal through `classifyNode`/`classifyToolResult`) — the fatal-code/gate-code machinery, the warning-prefix table, and the whole test suite are sound and worth keeping. But `activity-severity.ts` alone does **not** cover object lifecycle, request-row, readiness-criterion, or membership status — those five other tone-mapping modules need to be consolidated onto the same `Severity`/tone vocabulary as a separate, explicit step, or D4 will be "implemented" in one place and still contradicted in the other five.
