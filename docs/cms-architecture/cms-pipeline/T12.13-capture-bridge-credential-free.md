**Phase 12 · depends_on: T12.8 (the pdf-tool capture plane), T12.9 (the CMS-Agent capture engine), the 2026-08-02 artifact bridge (`7d1640ce`) · mode: auto · model: claude-opus-5 · effort: xhigh**

## Context — what was actually broken (verified live 2026-08-17)

Three facts, in the order they compound:

1. **`capture.crawl` could not call pdf-tool.** It invoked `create_capture_job`
   with no `storage` argument, and pdf-tool refuses every storage-touching call
   without one (`STORAGE_GRANT_REQUIRED`): it holds no storage credentials of its
   own since the server-side `CLIENT_*`/`PDF_TOOL_*` env fallbacks were removed.
2. **The T12.9 fix for that was a dead end.** CMS-Agent branch `t12-9-grant-wiring`
   (commit `09eb215`) fetched `get_pdf_tool_storage_grant` from the target and
   forwarded it. That RPC was **DELETED from platform core on 2026-08-02**
   (`7d1640ce`) and replaced by a server-side artifact bridge that mints the grant
   internally and never returns it — `grep -rn get_pdf_tool_storage_grant
   packages/core/server/` returns nothing. CMS-Agent's `platform` record still
   lists it `"allowed"`: a stale policy row, not a capability.
3. **There was no capture bridge at all.** `grep -rln create_capture_job
   packages/core/` returned nothing, so no tenant was reachable by the capture
   plane by any route.

Underneath all three sat the thing Wolf actually objected to. The credentialed
route needs `PDF_TOOL_STORAGE_SITE_ID` + `PDF_TOOL_STORAGE_TOKEN` — a **dedicated
Netlify Blobs PAT minted by hand in the console, per tenant**. Provisioning
auto-mints `PUBLISH_SECRET`, `MCP_HTTP_AUTH_TOKEN`, `ARTIFACT_UPLOAD_TOKEN_SECRET`,
`TRACKING_SALT` and `PURCHASE_TOKEN_SECRET`; that pair is one of the two
human-supplied per-site secrets left (the other being Stripe). It was outstanding
for zilberman on the day this task was written. Wolf ratified **option A** on
2026-08-14 rather than repeat that console step for every future tenant.

## The ruling this implements

> **Wolf, 2026-08-14: "option A, same-site writes."** Capture auth must need no
> per-site Netlify PAT.

## Decisions

### D1 — Option (a): pdf-tool writes only its own store. Zero cross-site credentials.

Three variants were on the table. The choice, and why the other two lost:

- **(a) CHOSEN — pdf-tool persists capture output same-site.** Its `health` already
  reports `blobStore.mode: "same-site"`; `jobBlobStore()` already resolves
  pdf-tool's own storage. So the capture plane writes its job records, screenshots
  and `snapshot.v1` into pdf-tool's own store, and the tenant imports what it wants
  afterwards through the artifact bridge that already exists. **No cross-site
  credential exists anywhere in the plane** — nothing to mint, nothing to rotate,
  nothing to leak, and nothing whose absence can block a new tenant. It is also the
  smallest change: no new auth mechanism, no new verification path, no new env var.
- **(b) exchange grant — REJECTED.** The tenant would sign an opaque value with the
  auto-provisioned `ARTIFACT_UPLOAD_TOKEN_SECRET` and pdf-tool would swap it at a
  tenant-side exchange endpoint. The swap has to return **a real Netlify Blobs
  credential for the tenant's site**, and the tenant has no way to mint one without
  … a PAT. The only value it could hand over is its runtime-injected Blobs context
  token — a live cross-site credential, i.e. exactly the "bearer that is just a PAT
  with extra steps" the brief forbids. It also adds a new authenticated endpoint to
  every tenant, and a new load-bearing env var, for no reduction in credentials.
- **(c) tenant-side writes — REJECTED on volume.** pdf-tool would return bytes and
  the tenant would persist them through its own injected Blobs context (genuinely
  zero credential). But a crawl produces a full-page **and** per-block screenshot
  per viewport per page — at the plane's ceiling of 50 pages × 2 viewports that is
  100+ PNGs, spread across multiple 15-minute worker windows. Moving them as
  base64 through MCP responses means tens of megabytes of JSON per crawl, through a
  transport whose standing rule is that binary bytes never travel through it, into
  a function with a fixed invocation budget, with the crawl's resume boundary now
  straddling a second service's write path. The failure modes are worse than the
  credential it removes.

`grantType` in pdf-tool's `storage-grant.ts` is documented as "a deliberate switch
point". Option A uses it as one: a new internal type
`pdf-tool-own-storage`, minted only by the capture plane, whose credential fields
are **non-credential sentinels** and whose real access resolves from pdf-tool's own
environment. Every downstream store opener keeps its single code path. The type is
deliberately **absent from `SUPPORTED_GRANT_TYPES`**, so `parseStorageGrant`
refuses a caller who names it: only pdf-tool can mint it, and only for its own
storage.

### D2 — The snapshot read path: a third bridge tool, `get_capture_snapshot`

A completed capture job's `result.snapshotArtifact` is an `ArtifactReference`,
never an inline `snapshot.v1`, and `captureCrawlStep` dead-ended at a typed
`capture_snapshot_unavailable` refusal. Under option A the bytes live in pdf-tool's
own store, so the tenant has no credential to fetch them with **and must not be
given one**. Handing out a signed URL would be the same mistake wearing a hat.

So the read goes through the plane that owns the bytes: pdf-tool gains
`get_capture_snapshot`, which reads its own artifact, checks the bytes against the
digest recorded on the job, and returns the **parsed `snapshot.v1` document**; the
tenant bridge exposes the same tool name and relays it. This does not breach "bytes
never travel through MCP": `snapshot.v1` is the crawl's structured DATA product
(pages, outline/blocks, diagnostics, the recorded policy and robots/rate evidence),
returned as JSON, not an artifact binary and not base64. Screenshots stay
`ArtifactReference`s and are never inlined; a snapshot over an 8 MiB inline ceiling
is refused (`CAPTURE_SNAPSHOT_TOO_LARGE`) with the reference still available for
import. Crawled content is data, never instructions — the bridge stamps that on
every response and nothing on either side interprets it.

### D3 — `site_id` is an OPTIONAL cross-check on the capture bridge

The one place this bridge's shape deliberately diverges from the artifact bridge's.
An artifact belongs to a `content_item` the caller has to name anyway; a capture
job belongs to nothing (it PRODUCES drafts), which is why it follows the lighter
`resolveTemplateBridgeScope` shape. But requiring the owning site object id would
mean every caller must know it, and CMS-Agent's registry has no field that reliably
carries it — `project.create` cannot set `objectDialect` at all, so a freshly
registered duplication target has none. Optional is strictly **safer**, not looser:
the answer is always this deployment's own site, resolved server-side from the
committed site-identity seam, and a caller that does supply one still gets the full
`capture_site_mismatch` refusal.

The pdf-tool **request scope** is not caller-nameable at all: the bridge derives it
as `capture_<sha256(siteId + "\n" + seedUrl)[0:24]>`. That is what gives a
re-driven crawl node pdf-tool's re-attach-instead-of-restart idempotency without
CMS-Agent having to know pdf-tool's tenancy model, and it means two tenants can
never collide in that scope.

### D4 — The bridge tools are `INTERNAL_ONLY_TOOLS`

Present and identical on every tenant's `/mcp` (that is fleet law) and callable
there, but deliberately absent from **agent discovery** — the documented
`INTERNAL_ONLY_TOOLS` mechanism, with direct precedent in
`create_artifact_from_url` (which the capture emitter itself calls) and
`capability_status` (which the fleet probe itself calls). Two reasons, both from
R-C5: the duplication capability is operated from CMS-Agent, and a crawl's bounds
come from the CMS-Agent project registry — tenant-side there is no registry, so an
autonomously-discovered crawl tool would take its origins from whoever called it.
This is a different axis from `OPTIONAL_HANDLER_TOOLS` (which is about per-site
handler presence): the surface stays uniform across all four tenants, so no
tool-uniformity ruling is required. **If Wolf wants them discoverable, deleting
three lines from `INTERNAL_ONLY_TOOLS` is the whole change** — note that the chat
wire-tool budget then sits at exactly its 64 cap.

### D5 — Bounds: three enforcement points, and the bridge can only narrow

R-C2 v2 keeps the CMS-Agent registry as the ONE operational policy home, so the
policy travels with the call rather than being duplicated tenant-side. That makes
the bridge the middle of three points: the registry authors the bounds, the bridge
re-checks the invariants and clamps, and pdf-tool's worker re-validates from the
stored record on every invocation. `capture-bridge-policy.ts` refuses
`sameOriginOnly !== true`, `respectRobots !== true`,
`authenticatedAccess !== "prohibited"`, `maxPages < 1`, empty origin/prefix lists,
a seed outside the policy the same call carries, and a policy SUBSET (`rights` /
`designReferences` / `fidelity` must all be present — the T12.9 defect, now failing
at the bridge with a bridge error code instead of three hops away). `maxPages` is
clamped to `CAPTURE_BRIDGE_MAX_PAGES` (50, mirroring pdf-tool's
`HARD_MAX_CAPTURE_PAGES_PER_JOB`). It deliberately does NOT reimplement pdf-tool's
full `parseCapturePolicy`: the complete shape gate stays single-sourced where the
crawl happens.

## What landed

**pdf-tool** (`t12-13-capture-bridge`):
`storage-grant.ts` gains `PDF_TOOL_OWN_STORAGE_GRANT_TYPE` + `pdfToolOwnStorageGrant()`
+ `isPdfToolOwnStorageGrant()`, and `grantBlobCredentials` gains that case (its
return type is now optional-field, so "no credential, use the same-site context" is
expressible). New `lib/capture/storage.ts` (`runWithCaptureStorage`) is the one ALS
frame every capture entrypoint runs its store work inside — and because
`storageGrantContext.run` REPLACES the ambient grant, a caller that still sends
`storage` cannot make the plane write with its credential. `agent-capture-mcp.ts`
wraps create/status and adds `getCaptureSnapshot`. `capture-worker-background.ts`
no longer requires a grant. `agent-artifact-worker-trigger.ts` never forwards the
own-storage grant. `mcp.ts` adds the three tools to `GRANT_OPTIONAL_TOOLS` and
`get_capture_snapshot` to the surface + capability manifest.

**platform** (`t12-13-capture-bridge`): new `capture-bridge-policy.ts`; three
`createPlatformCaptureJob` / `getPlatformCaptureJobStatus` /
`getPlatformCaptureSnapshot` client calls (the only calls in `pdf-tool-client.ts`
besides `health` that forward no grant); three handlers in `mcp-tool-handlers.ts`;
three definitions + `INTERNAL_ONLY_TOOLS` entries; dispatch in `mcp.ts`; a
`capture_bridge` real-read in the fleet capability probe.

**CMS-Agent** (`t12-13-capture-bridge`): `captureCrawlStep` calls the TARGET's
bridge; the grant fetch/forward/redact/scrub module is deleted; the snapshot read
path replaces the dead end. **Kept from `09eb215`:** the full canonical policy
travels VERBATIM, the authority gate runs first, refusals stay catalogued, and the
radioactivity discipline survives as `stripCredentialShapedFields` — belt and
braces over a remote that echoed something, even though under option A neither side
has anything to echo. The `projectId` and `requestId` fixes are kept in substance
and improved: both are now derived server-side by the bridge, so a caller cannot
name either.

## Laws

**P1 (core change = fleet change):** satisfied without touching any
`sites/<client>` file. This change adds no repo-tree file, no `netlify.toml`
setting, no seed-pack entry and no env var, and deploys no new per-site function
shim — the three tools are core dispatch over the existing `/mcp` front door, so
all four tenants get them from one place. Proven by `audit-site-admin-parity.mjs
--all` PASS at full check count ×4 (19 checks × 4 sites = 76 rows).

**P2 (new env var):** **no new env var.** Capture is gated only by the
fleet-shared `PDF_TOOL_BASE_URL` + `PDF_TOOL_AGENT_RUN_TOKEN` pair — capability
family `pdf_bridge`, already in the T11.7 table, already in `ENV_CHECKLIST`, both
marked `inheritFromPdfTool` so provisioning inherits them automatically. The change
REMOVES a load-bearing per-site pair from a path rather than adding one. Probe
coverage was still extended, because the capability this change makes load-bearing
could otherwise go unprobed: the existing `pdf_bridge` real-read is gated on
`pdf_storage_grant` ALSO being configured, so on the exact tenant this task
unblocks (no per-site PAT) it is skipped. The new `capture_bridge` real-read runs on
`pdf_bridge` alone, reads `get_capture_job_status` with a deliberately unknown job
id, and treats pdf-tool's own `CAPTURE_JOB_NOT_FOUND` as proof the credential-free
path is live — with `STORAGE_GRANT_REQUIRED` called out explicitly as "the deployed
pdf-tool predates T12.13". It is reported as its own line rather than an eleventh
`capability_status` family, because a family is a set of env-var names and capture
introduces none.

**Drafts only:** untouched. The capture plane still cannot reach
`object_publish` / `release_to_production` / `trigger_netlify_build` / deploy;
`create_capture_job` is `toolClass: 'draft'`, the two reads are `'read'`.

**Secrets:** no grant, token or site id is returned by any bridge tool, logged,
put in a warning or error string, written to run state, or written into an
artifact. Tested against a pdf-tool that echoes credential-shaped fields back.

   a deploy), the pdf-tool capture plane changed where it writes, and CMS-Agent's
   `capture.crawl` points somewhere new. Until pdf-tool is redeployed the capture
   bridge will answer `STORAGE_GRANT_REQUIRED` — which the fleet probe now names
   explicitly as "the deployed pdf-tool predates T12.13".
4. **Optional:** if `PDF_TOOL_SITE_ID` / `PDF_TOOL_BLOBS_TOKEN` are set on
   pdf-tool's own site, capture writes go through them (the same resolution
   `jobBlobStore` already uses for pdf-tool's own state); if unset it falls back to
   the built-in same-site context. Nothing to do unless a live crawl reports
   "The environment has not been configured to use Netlify Blobs".
5. **Not a blocker any more:** the outstanding "dedicated pdf-tool storage PAT +
   machine account for zilberman" item can be dropped from the capture critical
   path. It is still needed for the ARTIFACT/template families, which are a
   separate question this task did not touch.
