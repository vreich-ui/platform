# T18.10 — Tier access gates: let publisher / editor / viewer into `/admin` (D1 from the T18.9 harness)

**Phase 18 · depends_on: T18.9 (Part A) · mode: notify · model: claude-fable-5 · effort: high**
**Blocks:** T18.9 Part B step 3 ("Editor lands in `/admin` with Editor nav") — Wolf's run will hit this on the first invite.
**Plan:** `docs/cms-architecture/18-membership-plan.md` §6 (the permission matrix), §1 F7.

## The defect (D1, found by `tests/e2e/membership.e2e.test.ts` on 2026-08-17)
W18 made `publisher | editor | viewer` real, assignable, audited tiers (T18.1 store, T18.3a UI, T18.6b tools) and plan §6 promises every tier can "sign in to `/admin`, see objects, read chat history, edit own profile". But every admin function's SIGN-IN gate is still the pre-W18 two-tier check — `isAdmin = roles.includes('admin')` (`request-roles.ts:58`) or the local `if (!roles.includes('admin')) return 403 'Admin access required'`:

`admin-users.ts:223` (so `me` / `update_me` 403 → the shell cannot even load for an editor, and the welcome tour cannot finish), `admin-auth-state.ts:34` (tier ∈ owner|admin|null), `admin-object.ts:70`, `admin-agent-chat.ts:287`, `admin-audit.ts:51`, `admin-taxonomy.ts:38`, `admin-release.ts:63`, `admin-governance.ts:189`, `admin-ask-ai-object.ts:77`, `admin-artifact-upload-intent.ts:46`. `publish-gate.ts` is NOT involved (byte-untouched, stays so).

Net effect today: an invited editor accepts, gets `active` + `editor`, and is then locked out of the whole workspace with "Admin access required". The E2E pins the current behaviour with two assertions marked `D1/T18.10: flip to 200 once the tier gates land`.

## Scope (security boundary — Fable, exhaustive tests, `publish-gate.ts` untouched)
1. `request-roles.ts`: add `isMember = roles.length > 0` (any tier incl. viewer) beside `isAdmin`; add a small `requireTier(roles, 'viewer'|'editor'|'publisher'|'admin'|'owner')` helper with the tier order viewer < editor < publisher < admin < owner (owner expands to admin+publisher already; `editor` and `viewer` are leaves — see `expandRole`).
2. Sign-in gate → `isMember` on: `admin-users` (session verbs `me`/`update_me`/`accept`; management verbs keep the core's `MEMBERSHIP_VERB_MIN_TIER`), `admin-auth-state` (report the real tier, five values), `admin-object` READ verbs (get/list/inventory/contract/preview/history), `admin-agent-chat` (create/list/get/send — viewer's tool registry becomes the read class only, per the plan's autonomy table; the run loop must refuse write tools for a viewer/editor server-side, not just hide them), `admin-audit` (read).
3. WRITE gates by tier: `admin-object` checkout/patch/create/discard/submit_review → editor+; review decide → `canDecideReview` (already excludes viewer); publish/release/`admin-release` → `publish-gate` (admin|publisher — unchanged); taxonomy writes → editor+; governance read → admin, write → owner (unchanged); artifact upload intent → editor+; ask-ai-object → editor+ (it writes).
4. UI: `AdminLayout`/`AdminShell` nav trimming per tier (viewer: no Publish/Release, no Users; editor: no Publish; publisher: no Users) — `use-current-user.ts` already carries `roles`; `admin-auth-state`'s tier feeds the header. `MaintenancePage`, `GovernancePage`, `AdminUsers` keep their Owner/Admin client gates.
5. Tests: per function, a table test — viewer/editor/publisher/admin/owner × read/write verb → 200/403; the E2E's two D1 assertions flipped to 200 and extended (editor finishes the welcome tour on their own session; viewer `me` 200 + `list` 403; editor `checkout` 200 + `publish` 403 via publish-gate); `users-roles.test.ts` env-precedence untouched; `publish-gate` pinned unchanged.
6. Docs: plan §6 "Server enforcement points" updated with the helper; `10-admin-workspace-plan.md` §8 pointer already there; state-of-play.
