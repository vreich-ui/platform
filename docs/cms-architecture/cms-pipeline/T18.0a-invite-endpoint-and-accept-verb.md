## Context
Platform-originated invites today write the store record and then hit the wrong GoTrue endpoint, so no e-mail is ever sent and the UI shows "invite email pending" forever. Separately there is no server verb an accept page can call to (a) preview an invitation before the user has a session and (b) finish membership activation with a display name after GoTrue has issued the session.

## Scope — files to modify / create
1. `packages/core/server/lib/user-invite.ts`
   - Change the GoTrue call to `POST ${identity.url}/invite` with body `{ email, data: { invited_by: opts.invitedBy, role: opts.role } }` (roles are NOT authorization here — `data` is informational only; the store stays the source of truth).
   - Treat `422 … already registered` / `already been invited` from GoTrue as `sent:false, error:'already_invited'` (not a throw), and any other non-2xx as before.
   - Add optional `resendIfExisting?: boolean` — when true and the record already exists with `status:'invited'`, fire the GoTrue invite again (GoTrue re-sends for an unconfirmed user) and append audit `reinvite_email`.
   - **F6 fix (minimal, pre-v2):** when re-inviting a record whose `status === 'disabled'`, set `status:'invited'` and audit `reinvite` with detail `disabled → invited`.
2. `packages/core/server/functions/admin-users.ts` — two new verbs:
   - `invite_preview` — **public (no auth)**, `{ token }` accepted but not validated (only GoTrue can validate it, and an unauthenticated request has no admin token to ask with). Returns `{ site: { name, slug }, policy: { min_password: 8 } }` and nothing user-specific; the accept page shows the e-mail *after* GoTrue accepts, from the session's `/user`. Document this limitation in the verb comment.
   - `accept` — **authenticated (the fresh JWT `/verify` returned)**, body `{ display_name }` (1..200). Uses the caller's verified e-mail. If a store record exists: flip `invited → active`, set `display_name`, stamp `user_id` + `last_seen_at`, audit `accept`; idempotent (a second call returns the same active record). If **no** record exists (the person was invited from the Netlify UI, plan §4.2): do **not** create or grant anything — respond `200 { user: null, needs_grant: true }`; the layout shows its existing forbidden panel with the copy "Ask an Owner to grant you a role" (T18.0b renders that; T18.2 turns it into the "unmanaged identity" reconcile flow). Bootstrap `ADMIN_EMAILS` callers take the existing `me` path unchanged.
   - Extend `requestSchema` accordingly; keep every existing verb byte-identical in behaviour.
3. `tests/netlify/user-invite.test.ts` — change the URL assertion to `/invite`; add: body carries `data.invited_by`; already-invited 422 → `sent:false, error:'already_invited'`; `resendIfExisting` re-fires; disabled re-invite flips to invited.
4. `tests/netlify/admin-users-accept.test.ts` (NEW) — drive `createHandler(binding)` with a fake `context.clientContext.user` and an in-memory store: accept flips invited→active with the name; accept with no record → `needs_grant:true`, store untouched; accept twice idempotent; `invite_preview` needs no auth and returns the site name.
