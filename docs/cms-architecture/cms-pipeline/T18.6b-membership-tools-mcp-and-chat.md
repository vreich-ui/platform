## Why this model / effort
Definition + wiring work over a gated core that T18.6a already proved. The care needed is in tool descriptions (agents read them) and approval-card copy. Opus medium.

## Read first
- `packages/core/server/lib/mcp-tool-definitions-2.ts` (definition style, zod → JSON schema, description conventions e.g. `object_contract`), `mcp-tool-handlers.ts` (handler map), `functions/mcp.ts` (~L1190 listing filter — membership tools must be **listed only when the caller is an OAuth human principal**; hidden from shared-token sessions so agents don't even see them), `agent/tools.ts` (`CHAT_TOOLS`, `ToolAutonomy`, `autonomyFloor`, approval-card summary functions), `admin/RunApprovalControls.tsx` + `admin/chat.tsx` (ApprovalCard rendering), `docs/cms-architecture/chat-controls-protocol.md`.
- Plan §7 for names/args/classes.

## Scope
1. **MCP tools** (in `mcp-tool-definitions-2.ts` + handlers): `member_list, member_get, member_audit, member_invite, invitation_resend, invitation_revoke, member_set_role, member_suspend, member_reinstate, member_remove, member_purge, ownership_transfer, membership_policy_get, membership_policy_set, member_export, membership_contract`. Args exactly per plan §7; every write takes `idempotency_key?` and `dry_run?` where the core supports it; `member_purge` requires `confirm: 'PURGE <email>'`. Descriptions: state the human-principal requirement, the Owner tier, and the dry-run-first recommendation in the first sentence — agents decide from descriptions.
2. **Listing filter**: membership tools appear in `tools/list` only for OAuth human principals; a shared-token call to one returns the same `403 membership_requires_human` (defence in depth — the core already refuses).
3. **Chat registry** (`agent/tools.ts`): class `Membership`, default `ask`, `autonomyFloor:'ask'` (governance cannot lower it), Owner-only at execution (the role wall), tools: `member_list/get/audit` (read, `auto` allowed for owner), `member_invite`, `member_set_role`, `member_suspend`, `member_reinstate`, `member_remove`, `invitation_resend/revoke`, `ownership_transfer`. Approval-card summaries in human copy: "Invite **jane@x** as **Editor** — an e-mail is sent by Netlify Identity", "Remove **Jane Doe** — keeps history, purges after 30 days, deletes their login" — with the dry-run result shown in the card.
4. **Governance page** (`admin/GovernancePage.tsx`): the chat-tools autonomy table shows the Membership class with the floor lock explained.
5. `membership_contract` reachable from both doors; add it to the platform site's `/mcp` self-documentation list if one exists (`sites/platform` docs the system through its own `/mcp`).
6. Tests: `mcp-tool-definitions.test.ts` — schemas validate sample args; listing filter by principal kind; `agent/registry-wiring.test.ts` — floor cannot be lowered; approval summary snapshots.
7. Docs: `docs/mcp-final-agent-sequence.md` (or wherever tool sequences are catalogued) gets a "Manage members" recipe: `membership_contract → member_list → member_invite(dry_run) → member_invite`.

## Deliver
"Invite Jane as editor", "make Alex a publisher", "remove Bob" work from admin chat and from an OAuth-bound MCP client, with approval, audit and dry-run.
