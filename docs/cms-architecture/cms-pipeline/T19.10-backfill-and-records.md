## Why this model / effort
A one-shot script plus the documentation obligations. Low risk, fully specified.

## Read first
- `packages/core/server/lib/requests/store.ts` (T19.1) — `createRequest`, `rebuildIndex`, and the rule that a registry write never fabricates state it cannot verify.
- `packages/core/server/lib/agent/chat-store.ts` `listChatDocs` — the one place chat history lives.
- The CMS-Agent `workflow_list_runs` contract: paged (`limit` ≤ 100, `page.nextCursor`), `status` and `startedAt` range filters, rows carrying `runId`/`workflowId`/`projectId`/`status`/`nodes`/`errors`/`approvalsRequired` — but **no** `requestId`, which is why the join below runs the way it does.
- `CLAUDE.md`'s "Definition of converted" §5: no record = not done.

## Scope
1. **Backfill script** `scripts/backfill-editorial-requests.mjs`, `--dry-run` by default: walk the site's chat docs, pull every `tool_result` event whose tool is `run_workspace_workflow` (and the other creators from T19.1 scope item 5), recover `request_id` + `run_id` + `created_by` + timestamps, and mint a request record per job. Join to CMS-Agent by `run_id` via `workflow_list_runs`/`workflow_get_run` for current state.
2. **Unjoinable rows**: a run with no discoverable request id, or a request id with no run, is registered with what is known and `status_reason` saying so — never guessed into `done`. Report counts of each class.
3. **Idempotent**: a second run changes nothing. Re-runnable per tenant.
4. **Terminal old jobs** are registered already-archived, so the first view of `/admin/requests` is the live desk, not a year of history. Say how many in the run report.
5. **Records** (this is the row that makes W19 "recorded"): `object-inventory.md` gains the editorial-request entry; `state-of-play.md` gains the W19 closeout entry; `19-editorial-requests-plan.md` gains a §12 "what shipped" section mapping F1–F10 to the row that closed each, in the style of `18-membership-plan.md` §1's status line; `docs/cms-architecture/FLEET-STATUS.md` updated if it tracks per-tenant capabilities.
6. **Runbook**: one paragraph in `docs/cms-architecture/site-provisioning-runbook.md` on what a new tenant's operator does about mail (verify a sending domain, set `MAIL_FROM`) — the one manual step W19 adds.

The list is true from day one, and the wave is written down.
