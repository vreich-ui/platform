# T18.6a — `handleMembershipVerb` core + the human-principal gate for MCP / chat

**Phase 18 · depends_on: T18.2, T18.4 · mode: notify · model: claude-fable-5 · effort: xhigh**
**Blocks:** T18.6b.
**Plan:** `docs/cms-architecture/18-membership-plan.md` §7 (tool table, gate rule, error catalogue), F4.

## Why Fable / xhigh
This opens membership mutation to two new front doors (admin chat, `/mcp`). The one rule that must hold under adversarial input: **no agent principal — shared `MCP_HTTP_AUTH_TOKEN`, self-declared `agent_name`, chat run without a captured human — can ever invoke a membership write**; only a verified human (admin JWT, or an OAuth principal bound to a Netlify Identity human with the required tier) can, and every call is audited with `via`. It is the same class of boundary as `publish-gate`. Interactive; `/effort xhigh`; adversarial tests first.

## Scope
1. `packages/core/server/lib/membership/verbs.ts` (NEW): `handleMembershipVerb(input: { verb, args, principal: Principal & { via:'admin_ui'|'mcp'|'chat' }, store, identity?, policy })` covering: `list, get, audit, invite, resend, revoke, set_role, suspend, reinstate, remove, purge, transfer_ownership, policy_get, policy_set, export, contract` (`contract` = the machine-readable `membership_contract`: roles, verbs, args schemas, policy, error catalogue — mirror `object_contract`'s derive-from-enforcing-code discipline).
   - **Gate, first line of the function:** `if (principal.kind !== 'human') → 403 membership_requires_human` — before any store read. Then tier check per verb per plan §6/§7 (`owner` for everything except `list/get` (admin) and `invite` of editor/viewer under `policy.who_can_invite`).
   - Every mutation → `AuditEvent{ via, actor, request_id }`.
   - `dry_run: true` supported on `invite`, `set_role`, `remove`, `transfer_ownership` (returns the would-be effect + policy check, persists nothing).
2. `functions/admin-users.ts` → thin: auth → build human principal `{kind:'human', id, email, via:'admin_ui'}` → `handleMembershipVerb`.
3. **MCP principal plumbing** in `functions/mcp.ts`: when `authResult.oauthPrincipal` is present, build `{kind:'human', id: subject_user_id, email: subject_email, via:'mcp', client_id}`; when only `verifiedAgentName`/shared token: `{kind:'agent', …}` (unchanged). Expose a `getCallerPrincipal()` to handlers (there may already be one for object verbs — reuse). **No tool definitions yet** (T18.6b) — but add the internal handler entry points so T18.6b is definition-only.
4. **Chat plumbing** in `agent/tools.ts` + `loop.ts`: the run record already carries the captured human `Principal` (T9.13); pass it with `via:'chat'` to `handleMembershipVerb`. Add an `autonomyFloor:'ask'` class `Membership` in the registry types (definitions themselves in T18.6b).
5. Tests (`tests/netlify/membership-verbs.test.ts`, adversarial first): agent principal ⇒ 403 on every verb incl. `list`; shared MCP token with `agent_name:'owner@…'` ⇒ still agent; OAuth principal whose subject is a suspended member ⇒ 403; OAuth admin (not owner) can `list` and invite editor only when policy allows, 403 otherwise; every audit event carries `via`; `dry_run` persists nothing; `contract` output validates against its own schemas; admin-users function behaviour byte-identical for the existing UI calls (fixture replay from T18.0a–T18.4 tests).
