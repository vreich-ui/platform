# T19.1 — Editorial request registry: store, `editorial-request.v1`, index, single-writer discipline

**Phase 19 · depends_on: — · mode: notify · model: claude-fable-5 · effort: xhigh**
**Blocks:** every other W19 row.
**Plan:** `docs/cms-architecture/19-editorial-requests-plan.md` §3 (and §5.1 for the status enum this schema must carry).

## Why this model / effort
Netlify Blobs has no compare-and-swap. `agent/loop.ts` solved that for chats with a single-writer state machine and one-shot trigger tokens; the request doc has *more* writers than a chat doc (a chat tool at creation, the sweeper on every transition, a human on archive/cancel) and the same class of lost-update and stuck-state failure modes. Get this wrong and every downstream row inherits a registry that silently drifts from reality — which is the exact defect W19 exists to remove. Correctness work: Fable, xhigh.

## Scope
1. **Store**: `packages/core/server/lib/requests/store.ts` — new per-site blob store `editorial-requests`, `consistency: 'strong'`, keys exactly as plan §3.2 (`requests/by-id/<request_id>.json`, `requests/index.json`, `requests/notify/<person_id>.json` reserved for T19.6). Key escaping follows `chatDocKey`'s rule.
2. **Schema**: `editorial-request.v1` per plan §3.3, zod, `schema_version` literal, every optional field schema-additive so a doc written before a later row still parses. `history` bounded to 50 entries with the same drop-oldest discipline `appendChatEvent` uses for events.
3. **Index**: `RequestIndex` doc holding only the projection in plan §3.3 (row fields named there and nothing more), a monotonic `seq`, and `updated_at`. Written by the same call that writes the request doc — never independently. Provide `rebuildIndex(store)` that regenerates it from the per-id docs and is safe to run at any time.
4. **Writers**: one exported function per legal transition (`createRequest`, `recordProgress`, `setStatus`, `attachChat`, `archiveRequest`, `cancelRequest`), each documenting *who* may call it per plan §3.4. No general-purpose `saveRequest` escape hatch. A transition that arrives out of order (a sweeper write for a request a human just archived) is a no-op that returns the current doc, not an overwrite.
5. **Mint-on-start wiring**: `run_workspace_workflow` creates the request record at the moment it starts a run — the request id it already mints, the run id/workflow id/project id it already receives, `created_by` from the run's human principal, `title` and `brief_excerpt` from `input.title`/`input.topic`/`input.instructions`. Do the same for the non-workflow creators named in plan D7 (`instantiate_template`, `instantiate_section_template`, `apply_theme`, `create_agent_artifact_job`) with no `workflow` block. Creation must never fail the tool call: a registry write that throws is logged and swallowed, because losing a record is worse than losing the job but far better than *not starting* the job.
6. **Tests** (`packages/core/server/lib/requests/store.test.ts`): schema round-trip incl. an old doc missing every optional field; index stays in lockstep across every writer; `rebuildIndex` reproduces a hand-built index byte-for-byte; out-of-order transition is a no-op; history trim; concurrent-writer fixture proving the last legal writer wins and an illegal one does not.

## Deliver
A request exists as a record the instant a job starts, with an index cheap enough to poll, and exactly one legal writer per transition.

## Non-goals
No sweeper (T19.3), no endpoint (T19.2), no UI, no notifications, no backfill of historical jobs (T19.10). Do not change `agent/loop.ts` or the chat doc schema.
