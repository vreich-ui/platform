## Scope
1. **Delivery state**: `requests/notify/<person_id>.json` (reserved by T19.1, written by T19.2's mute action) gains `last_notified: Record<request_id, status>` so a reload or a second tab never re-announces the same transition. Cap its size and prune entries for archived requests.
2. **In-app**: the shell's poll compares the index against `last_notified`; new transitions raise a toast with an **Open** action deep-linking to the request. Unread count goes in `document.title` as `(N) …`, cleared on visiting `/admin/requests` or opening the request.
3. **Browser notifications**: `Notification` API. Permission is requested **once**, from an explicit "Notify me" control on `/admin/requests` — never on page load, never from the shell. Fire from the same comparison, dedup through the same `last_notified`. Click opens the deep link and focuses the tab. If permission is denied, the control says so and offers nothing further.
4. **Preferences** on the W18 `Person` record: `notify: { email: 'immediate' | 'daily' | 'off', browser: boolean }` with plan D4's defaults, edited on `/admin/profile`. This row writes and reads the field; T19.7 consumes the `email` half.
5. **Honesty about the limit**: the UI states plainly that browser notifications only arrive while an admin tab is open, and that closed-browser push is not built (plan D5). One sentence, next to the control.
6. **Tests**: the transition→notification decision as a pure function (fixtures for every status pair, incl. the ones that must NOT notify); dedup across two simulated tabs; `document.title` restore.

## Deliver
An editor who leaves the tab open learns within one poll that a job needs them, stalled, failed or finished — without reading the list.

## Non-goals
No e-mail (T19.7). No service worker, no Web Push, no VAPID (V2, plan D5).
