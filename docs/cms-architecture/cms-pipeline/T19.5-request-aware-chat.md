## Why this model / effort
This is the row that makes the chat manager able to talk about a specific job — Wolf's "any req should lead to its instance appearing in the AI window with chat manager being able to distinguish and start to communicate about a specific req". It touches the two most-used components in the admin (`chat.tsx`, `AgentsHub.tsx`) plus the send path. Opus, high.

## Scope
1. **Binding**: a chat may carry `request_id`. `send` attaches the chat to the request (T19.1's `attachChat`) the first time, and `create_chat` accepts an optional `request_id`. A request with no chat yet mints one on first open.
2. **`focus` injection**: when a chat is bound to a request, the server composes `focus` from the request record per plan §7.1 — status, progress, current/last node, the failure code where there is one, who asked — inside the existing 500-char bound, truncating the least useful part first. A workspace-supplied focus (the object rail) is appended after the request line, not replaced. No wire change.
3. **Request header card** above the transcript in both mounts (`AgentsHub` panel and `AgentRail`): title, status pill, progress bar + current node label, `status_reason`, blockers verbatim on `needs_you`, and the state-appropriate actions (Retry, Open article, Archive, Approve & continue where the pending approval is the chat's own). Reuse `RunApprovalControls`' placement conventions; do not duplicate the approval card.
4. **`request_progress` rendering**: the event type T19.3 appends renders as a compact timeline line inside `groupChatEvents`' activity grouping — quiet by default, expandable, and present after a reload because it is persisted.
5. **`run_finished` copy (F1/F2)**: stop returning `null`. Render one line keyed on `detail.outcome` — `completed`, `cancelled`, `error`, and specifically `caps`: *"I paused this turn — the job is still running. It will keep going; I'll report when it moves."* Never let a run end with a silent transcript again.
6. **New conversation about this request**: an affordance on the header card that mints a fresh chat attached to the same request, so a second line of questioning does not pollute the first transcript.
7. **Routing**: `/admin/requests/<id>` mounts the request's most recent chat; `?request=<id>` does the same on the hub. Both cold-load correctly.
8. **The hub's session list**: demote it. `/admin/requests` is now the list; the hub keeps starters + the active conversation and links out to the list. State in the commit body what you removed.
9. **Visibility alignment**: with requests team-wide (plan §8), decide and document what a colleague opening someone else's request sees of the transcript. Default: the transcript is readable to any signed-in admin who can see the request, and `chat-visibility.ts` is updated with a comment recording the change. This is a deliberate change to an existing security-shaped rule — call it out explicitly in the commit body.
10. **Tests**: focus composition (incl. truncation) as a pure function with fixtures; `run_finished` copy per outcome; `request_progress` grouping; the binding path.

## Deliver
Clicking any request in the list opens a conversation that already knows what the job is, what state it is in, and what to offer next.
