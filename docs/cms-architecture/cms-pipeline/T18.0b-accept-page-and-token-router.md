## Why this model / effort
Client-side auth flow across four GoTrue token types, touching the header script every public page loads and the admin gate. Well specified, but the failure mode is "nobody can get in" — Opus, high effort, run the build and the browser smoke locally before committing. Not Fable: no server authority changes.

- GoTrue: `POST /verify {type:'signup', token, password}` → `{access_token, refresh_token, expires_in, token_type}` (invite acceptance; password required); `POST /verify {type:'recovery', token}` → same session shape; `PUT /user {password}` / `PUT /user {data:{full_name}}` with the session bearer; e-mail change: `POST /verify {type:'email_change', token}`. Default mail hashes: `#invite_token=`, `#confirmation_token=`, `#recovery_token=`, `#email_change_token=`.

## Context
Invitees land on `/` with `#invite_token=…` and nothing reads it. Recovery links carry `#recovery_token=…` while the client expects `type=recovery&access_token=`. There is no page where a new member can set a password and a name.

## Scope — files to create / modify
1. `packages/core/lib/admin/goTrueClient.ts`
   - `export const detectIdentityToken = (hash = location.hash): { kind:'invite'|'confirmation'|'recovery'|'email_change'; token:string } | null` — reads the four hash keys; **does not** clear the hash.
   - `export const acceptInvite = async (token, password) => GoTrueUser` — `POST /verify {type:'signup', token, password}`; on success `fetchUserInfo` + `writeStorage` (same as OAuth path).
   - `export const exchangeRecoveryToken = async (token) => GoTrueUser` — `POST /verify {type:'recovery', token}`; write storage; the caller then uses `updatePasswordWithToken(user.token.access_token, pw)`.
   - `export const setFullName = async (fullName) => void` — `PUT /user {data:{full_name}}` with the current session.
   - Keep `handleRecoveryCallback` working for the `type=recovery&access_token` shape (in case a site's template was customised to it) **and** make it also accept `#recovery_token=` by exchanging via `exchangeRecoveryToken`. `handleOAuthCallback` must keep ignoring all four token hashes.
2. `packages/core/app/components/common/HeaderAuthButton.astro` — at the very top of `initializeHeaderAuthState`: `const t = detectIdentityToken(); if (t && !location.pathname.startsWith('/admin/accept')) { location.replace('/admin/accept' + location.hash); return; }`. This is the site-wide router: whatever page a default e-mail template lands on, the token reaches the accept page intact (hash survives `replace`).
3. `packages/core/app/routes/admin/accept.astro` (NEW) — **not** on `AdminLayout` (no auth gate; the person has no session yet). Use the public `Layout` the site uses for system pages, minimal chrome, `noindex`. Mounts island `~/admin/AcceptInvite` with `identity` prop (D2 pattern).
4. `packages/core/admin/AcceptInvite.tsx` (NEW, kit components from `~/admin/primitives|forms`) — state machine by `detectIdentityToken().kind`:
   - `invite`: form **Full name**, **Password** (min 8, show/hide), **Confirm password** → `acceptInvite(token,pw)` → `setFullName(name)` → `usersClient.acceptInvite(getToken, {display_name:name})` → if `needs_grant` show "You're signed in, but no role has been granted on this site yet — ask an Owner." with a Sign-out button; else redirect `/admin/welcome` if it exists (T18.5) else `/admin`.
   - `recovery`: **New password** + confirm → `exchangeRecoveryToken` → `updatePasswordWithToken` → toast → redirect `/admin`.
   - `confirmation` / `email_change`: `POST /verify` with the matching type, then redirect `/admin` (email_change: also call `usersClient.me` so `last_seen` stamps; the store re-index is T18.1).
   - No token / expired (GoTrue 4xx): friendly error + "Ask the person who invited you to send a new invitation" + link to `/`. Never render the raw token.
   - After success, `history.replaceState` to strip the hash.
5. `packages/core/lib/admin/users-client.ts` — `acceptInvite(getToken, {display_name})`, `invitePreview()`.
6. `packages/core/app/layouts/AdminLayout.astro` — forbidden panel copy gains the "no role granted yet" line when `admin-auth-state`/`me` reports no roles for an authenticated user (keep the existing structure).
7. **P1**: `/admin/accept` must exist on every tenant. Verify the route is served by core for all four `sites/<client>` (the S1 admin routing already maps `/admin/*` to core routes — confirm with `node scripts/audit-site-admin-parity.mjs --site sites/<client>` for each; if the audit enumerates admin routes, add `accept` to its expected list).
8. Tests: `packages/core/lib/admin/goTrueClient.test.ts` — extend: `detectIdentityToken` for all four hashes and none; `acceptInvite` posts `type:'signup'` with password and writes storage; `exchangeRecoveryToken` posts `type:'recovery'`; OAuth callback ignores token hashes. Add a jsdom-free unit for the router predicate (extract `shouldRouteToAccept(pathname, hash)` as a pure function in `goTrueClient.ts` and test it).

## Deliver
Any Netlify Identity e-mail link (default template or custom) ends on `/admin/accept`, where the person sets password + name and lands in the workspace with an active membership.

## Non-goals
