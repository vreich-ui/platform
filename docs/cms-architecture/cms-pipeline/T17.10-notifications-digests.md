# T17.10 — Notifications / digests (deferred item 13)

**Phase 17 · depends_on: T17.6 · mode: checkpoint · model: Sonnet 5 · effort: medium**
**Blocks:** —.

> ## ⛔ OPEN QUESTION — this task does not start until Wolf answers
>
> **What is the delivery channel, and what is the cadence?**
>
> This is a product decision, not an agent one, and it is the only item in
> W17 with no obvious default. The options, each with its real cost:
>
> - **(a) In-app only.** An attention inbox at `/admin` listing open threads
>   across every object. No new infrastructure, no new env vars, no
>   deliverability problem. Nobody finds out about a comment unless they log
>   in.
> - **(b) Email digest.** One scheduled message per recipient — "3 threads
>   need you". Needs a mail provider, a new env var per site (W16 law P2:
>   the env table + `ENV_CHECKLIST` + every existing site's env + the
>   capability probe, in the same change), an unsubscribe path, and a
>   cadence.
> - **(c) Push (ntfy/Slack webhook).** The `cms-pipeline/notify.sh` pattern
>   already in the repo. Cheapest of the two out-of-app options; per-person
>   configuration rather than per-site.
> - **(d) Both (a) + one of (b)/(c).**
>
> **Sub-questions the answer must also settle:** immediate or digest;
> per-thread or per-object rollup; who is notified (thread participants, the
> object's assigned agent's human owner, all Owners); and whether an
> **agent-authored** reply notifies a human (T17.7 makes agent replies
> routine — under an immediate policy that is the highest-volume source).
>
> Nothing below is built until this is answered. **Per plan §5, T17.10 stays
> parked; it does not block any other W17 task.**

## Context

Marginalia's whole value is asynchronous review; asynchronous review with no
notification is a folder nobody opens. But the delivery mechanism has cost,
fleet-parity and privacy consequences that only Wolf can price.

## Scope — pending the answer, this is the shape

- **Notifiable event:** an open thread that has had no reply from the
  notified party since it was created or last replied to. Derived from the
  same definition `Attention N` uses (spec §4.1) — one definition, two
  consumers.
- **Enumeration:** a server-side sweep over the marginalia index, reusing the
  `listAllObjectRecords` resilience pattern (per-type failure degrades to
  zero from that type, never fails the sweep).
- **Delivery adapter behind one interface**, so the channel chosen in the
  ruling is one implementation and the others stay possible: `deliver(recipient,
  digest)`.
- **Per-site configuration** honouring W16 P2 if any env var is introduced:
  the T11.7 env table, `ENV_CHECKLIST`, all three `sites/<client>` envs, and
  the capability probe — in the same change, or an explicit catalogued
  `error_code` degradation.
- **Respect T17.11's visibility policy**: a digest must never name a thread
  its recipient cannot read.
- **Unit tests (`node:test`):** digest assembly from a thread fixture
  (who gets what), the "already replied" suppression, and the
  visibility filter.

## Acceptance criteria

- The delivery channel matches Wolf's ruling and is recorded in
  `docs/cms-architecture/decisions/` in the same change.
- No digest names a thread the recipient cannot see.
- Any new env var is fleet-complete per P2, or the feature degrades with a
  catalogued `error_code`.
- Committed `T17.10: …`; no PR.

## Non-goals

No client-side polling (spec §8.5). No read receipts or per-user read state —
the store has none and this task does not invent one. No notification
preferences UI in V1 beyond on/off.
