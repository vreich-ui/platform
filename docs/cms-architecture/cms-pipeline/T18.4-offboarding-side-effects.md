# T18.4 — Offboarding: token revocation, lock hand-off, identity delete, purge sweep, ownership transfer, export

**Phase 18 · depends_on: T18.1, T18.2 · mode: notify · model: claude-fable-5 · effort: high**
**Blocks:** T18.6a (tools call these verbs), T18.9.
**Plan:** `docs/cms-architecture/18-membership-plan.md` §5 (the three verbs table), F5, F12; governing decision §9-3 (**delete identity on remove: default true**, behind `delete_identity` flag).

## Why Fable / high effort
Touches the OAuth store (revocation of live MCP grants), forced lock release under another principal's name (history attribution), and hard deletes in GoTrue + a scheduled purge that scrubs PII. Wrong scoping here either strands a live editing session, deletes the wrong identity, or leaves a removed member with a working MCP token. Interactive; `/effort high`.

## Scope
1. `packages/core/server/lib/membership/offboarding.ts` (NEW):
   - `revokeOAuthGrantsForSubject(store, subject_email)` — list + delete every access/refresh/code/pending record whose `subject_email` matches (add an `oauth/by-subject/<email>/…` index in `oauth-store.ts` if listing by prefix is the only way; write it on mint from now on, and back-fill lazily on read).
   - `releaseLocksHeldBy(person)` — enumerate held leases (via `object_inventory` lock state) whose holder is the person and force-release each, history entry `lock_forced_on_offboarding` attributed to the acting Owner with `on_behalf_of` the removed person.
   - `deleteIdentity(identity, gotrue_user_id)` — `DELETE /admin/users/{id}`; idempotent on 404.
   - `scrubPerson(person)` — PII → `{ person_id, deleted:true, deleted_at }`, indexes removed, avatar artifact soft-deleted, memberships kept as `removed`, audit kept (actor stays `person_id`).
   - `transferOwnership(from, to)` — both must be active; `to` becomes owner; `from` becomes admin unless the caller says otherwise; audit both.
   - `exportPerson(person)` — JSON bundle: person, memberships, invitations, audit slice, list of object-history entry ids authored (from the object store history, ids only).
2. Verbs in `admin-users.ts`: `suspend` now also revokes OAuth grants + releases locks; `remove` = suspend effects + membership `removed{purge_after}` + `delete_identity` (default `policy.delete_identity_on_remove = true`) + pending invitation revoked; `purge` (Owner, typed confirm string `PURGE <email>` verified server-side); `transfer_ownership`; `export_person`; `queue_identity_deletes` drained at the start of any Owner request that carries an identity admin token.
3. `packages/core/server/functions/membership-sweep.ts` (NEW scheduled, daily): `expireAll` (T18.2), purge memberships past `purge_after`, drain queued identity deletes if a token can be obtained (it cannot in a scheduled invocation — so it only *marks* them and the next Owner request drains; log that). Declare the schedule in `netlify.toml` and every `sites/<client>/netlify.toml` (P1); add the site shim `sites/<client>/netlify/functions/membership-sweep.ts` following the `mcp-keepalive` pattern; extend `scripts/audit-site-admin-parity.mjs` to require it.
4. Tests (`tests/netlify/membership-offboarding.test.ts`): revoke removes exactly the subject's grants and nobody else's; a revoked refresh token fails at `mcp.ts` principal resolution; force-release writes history with `on_behalf_of`; remove with/without identity token (queued vs immediate); purge scrubs PII and keeps audit; `last_owner` on remove/transfer; export bundle shape; sweep idempotent; policy flag off ⇒ identity kept.

## Deliver
Suspend/remove/purge do what the members page promises; no removed member keeps a working token, a lock, or an identity (when the policy says so).
