## Why this model / effort
The sending code is small. The obligation around it is not: this is the platform's **first** outbound mail dependency, and W16 law P2 says a new env var read by core lands, in the same change, in the T11.7 env table + `ENV_CHECKLIST` + every existing site's env (or degrades with an explicit catalogued `error_code`) and is covered by the capability probe. Four vars × four tenants, a new capability family, and a degrade path that must be genuinely safe. Opus, high.

## Scope
1. **Seam** `packages/core/server/lib/mail/`: a `MailSender` interface (`send({ to, subject, text, html?, tags? })` → `{ ok } | { ok: false, code, message }`), a `NullMailSender` used whenever unconfigured, and `resolveMailSender()` reading env at call time (never at import time).
2. **Adapter**: Resend over plain `fetch` — one endpoint, no SDK, no bundle cost (plan D3). Bounded timeout, typed errors, no retry storm; a send failure is logged and recorded on the request's `history`, never thrown into the sweep.
3. **Env** `MAIL_PROVIDER` (per-site, `resend|none`, default `none`), `MAIL_API_KEY` (fleet-shared), `MAIL_FROM` (per-site), `MAIL_REPLY_TO` (per-site, optional). Add all four to: the T11.7 env table, `ENV_CHECKLIST` with real notes, and the probe's env→family map under a new `mail` family added to both `CAPABILITY_FAMILIES` and `capability-status.ts`.
4. **Degrade**: unconfigured is normal, not broken — `error_code: 'mail_not_configured'`, catalogued alongside the existing codes, in-app and browser channels unaffected, and the capability probe reports `mail` as unconfigured rather than failing. A tenant with no mail must behave exactly as it does today.
5. **Delivery**: consume T19.3's transition record and T19.6's per-person `notify.email` preference. `immediate` sends on `needs_you`/`stalled`/`failed`; `done` follows the digest setting. Build the immediate path fully; land the daily digest as a second pass over the same transition log on the existing daily schedule slot, or state plainly in the commit body that it is deferred and to which row.
6. **Content**: thin by design — what happened, which request, one deep link, one unsubscribe/preferences link. No article body, no transcript, no PII beyond the recipient's own address. Plain text with an optional minimal HTML part.
7. **Tests**: `NullMailSender` chosen when unconfigured; adapter request shape pinned; failure recorded not thrown; preference routing per fixture; a parity test asserting every new var appears in `ENV_CHECKLIST` **and** the probe map (extend `tests/scripts/*parity*` rather than inventing a new harness).

## Deliver
The platform can send an editor an e-mail when their article needs them — and a tenant without mail configured behaves exactly as it did before.

## Non-goals
No marketing/transactional mail beyond request notifications. No template designer. No inbound mail. Domain verification per tenant is Wolf's click (T19.11).
