## Context

Today, changing a word means: hover → chip → pencil → panel → form field →
save. The concept removes all of that for the common case. This is the
interaction Wolf works in, so it has to be exactly as cheap as the PDF says.

## Scope

- **Enter:** `dblclick` on an annotated region (`[data-cms-node-id]`,
  `[data-cms-section-id]`, `[data-cms-nav-object]`, innermost first — the
  same resolution order the hover listener uses) mounts an inline editor
  over the block's **primary copy field**.
- **Primary field derivation, not a hardcoded map:** the first field
  `formFieldsFor(data, 'edit')` would render for that block, skipping
  `NON_COPY_KEY_RE` matches. A block with no such field (image node, grid,
  most `navigation` targets) falls through to `openPanel(target, region,
  'edit')` — spec §5.1.
- **Editor choice:** `rich_text.v1` bodies → `createRichTextEditor` (grammar
  allowlist, sanitizer and https-only links come with it, unchanged).
  Plain-string bodies and single-line fields → a contenteditable bound to
  the same field, no toolbar.
- **Persist through the existing path only** — there must be no second write
  path. `Cmd/Ctrl+Enter` or blur commits via `EditSession`:
  `ensureCheckout()` → `patch([{op:'update_node', node_id, fields:{public:…}}])`
  or `update_section_data`, then `invalidateRecord`, mark the region
  `dl-em-draft`, `refreshPending()`. `Esc` reverts to the entry value with no
  write. A held lock refuses with the existing
  `Locked by X — try again when the lock frees.` status and the block returns
  read-only.
- **The three collisions**, each fixed per spec §5.3:
  1. `mouseup` selection capture is **skipped when `event.detail >= 2`**, so
     a double-click's word selection is never mistaken for an Ask-AI scope.
  2. While a block is in inline edit, its own bubble stays pinned; other
     blocks' hover-reveal and gutter-marker hover are suppressed until edit
     exits.
  3. `click` on an in-content anchor is `preventDefault()`-ed in edit mode.
- **Keyboard equivalent** (spec §9): `Enter` on a focused annotated block
  enters inline edit; `Esc` reverts; `Cmd/Ctrl+Enter` commits. Annotated
  blocks become focusable in edit mode only.
- **Outside click commits** (blur), with the save reported on the status
  line.
- **Unit tests (`node:test`, no DOM harness):** primary-field derivation from
  a `data` object + mode, the `event.detail >= 2` selection-suppression
  predicate, and the value→ops mapping for both node and section targets.

## Acceptance criteria

- Against the PDF: double-clicking a paragraph puts a cursor in it and typing
  changes it; no panel opens at any point; the change lands as a draft on the
  same reviewable verb path a panel save uses (verified in the object's
  history, not just on screen).
- Double-clicking never leaves a stray Ask-AI selection scope armed; the
  Ask-AI chip's "about selection" state is unchanged for real single-drag
  selections.
- Double-clicking a link edits, does not navigate.
- Rich-text blocks keep grammar enforcement: an out-of-grammar paste is
  stripped client-side exactly as the panel editor strips it.
- Locked object → refusal, no partial write, block read-only again.
- `npm run check` and `npm test` green. Committed `T17.8: …`; no PR.

## Non-goals

No new field grammar, no widening of `rich_text.v1`. No image editing inline
(the Image panel section keeps that). No multi-field inline forms. No
autosave-on-keystroke — commit points are explicit (spec §5.2). No changes to
the marginalia verbs or store.
