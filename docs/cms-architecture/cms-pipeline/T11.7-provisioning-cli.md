# T11.7 — Provisioning CLI: `create-site` (new client = one command + DNS)

**Phase 11 · depends_on: T11.6 · mode: auto · model: Opus 4.8 · effort: high**
**Blocks:** T11.11.

## Read first

`docs/cms-architecture/11-platformization-plan.md` §2.4, `netlify/lib/blob-store.ts` (store set + env binding), `scripts/provision-pdf-tool-stores.mjs` (the write→read→delete probe pattern), the T11.5 site-config schema, `docs/agents/pdf-tool-storage-grant.md` (machine-account/rotation posture to mirror).

## Context

"New client" must be scripted, not tribal: scaffold the site dir, create/bind the Netlify site, provision stores, seed the baseline pack, emit the env checklist. Steps needing account authority emit precise human instructions instead of failing silently.

## Scope — files to create/modify

- ✡ `packages/core/cli/create-site.mjs`: `--name <client>` → scaffold `sites/<client>/` (site.config template, netlify.toml, empty data tree, baseline seed pack: site singleton, nav skeleton, taxonomy skeleton, default theme, starter recipes — parameterized copies of the canonical seeds with `<client>` ids); with `--netlify-token`, create the Netlify site via API, run the store write-probe, print the env checklist (**the real per-site env table below** — not an illustrative subset) — values generated where safe, placeholders + instructions where human-owned. `--dry-run` prints the full plan.
- Idempotent re-runs (existing dirs/sites detected, never clobbered); secrets never written to disk or logs — checklist references env names only.
- ✡ `docs/cms-architecture/site-provisioning-runbook.md`: the human half (Netlify account, DNS, Identity/admin bootstrap via `ADMIN_EMAILS`, secret storage).

## Per-site env table (the checklist `create-site` emits)

Enumerated from a 2026-07-22 census: every `process.env.*` / `env.*` /
`Netlify.env.get(...)` read across `src/`, `netlify/`, and `mcp/` (~35
config vars once platform-injected build vars and pure ops knobs are set
aside). **This table is the shared source of truth for the T11.7 provisioning
checklist AND the T11.10 per-site governance/secrets inventory** — keep the
two in sync. Classification: **per-site** (unique per client), **fleet-shared**
(one value across all clients — the platform/service creds), **optional**
(feature-gated or has a safe default), **platform-injected** (Netlify supplies
at runtime — do not set by hand).

### Second/third tenancy axes — pdf-tool + tracking (per-site keys over shared services)

| Env                        | Class                | Notes                                                                                        |
|---|---|---|
| `PDF_TOOL_PROJECT_ID`      | per-site             | **Second tenancy axis:** the client's project id inside the pdf-tool (resolver `pdfToolProjectId`, defaults to the site slug). Distinct from the Netlify site id. |
| `PDF_TOOL_BASE_URL`        | fleet-shared         | Base URL of the shared pdf-tool service used by Platform's server-side artifact bridge. |
| `PDF_TOOL_AGENT_RUN_TOKEN` | fleet-shared         | Server-to-server bearer used only by the Platform bridge; never exposed to MCP clients. |
| `PDF_TOOL_STORAGE_SITE_ID` | per-site             | The storage grant target (Netlify site id) pdf-tool writes this tenant's templates/artifacts/image-search state into. **Not fleet-shared by default** — each tenant should get its own dedicated value (see `docs/agents/pdf-tool-storage-grant.md`'s provisioning steps). Status as of 2026-08-05: `platform` and `fernwell` each have their own dedicated pair (fernwell's live-verified via a real create/list/deactivate round trip); `dr-lurie`'s `SITE_ID` has always resolved to itself so it already passes the letter of the rule, though its token is the one that used to be handed around as the fleet-shared credential — rotating it too is an open hygiene question, not a confirmed gap. **Enforced, not just documented**: `create-site --known-tenant-site <name>` (repeatable) refuses to finish provisioning if this site's value collides with a named sibling's; `node scripts/audit-storage-grant-parity.mjs --site … --site …` audits an already-live fleet the same way. |
| `PDF_TOOL_STORAGE_TOKEN`   | per-site             | Auth paired with `PDF_TOOL_STORAGE_SITE_ID` above — same per-tenant rule, same current status. **Since T12.13 (2026-08-17) this pair is NOT a capture blocker**: Wolf's 2026-08-14 "option A, same-site writes" ruling means the capture bridge carries no storage grant at all (pdf-tool persists crawl output into its own store), so a tenant with this pair unset can still be captured end to end. It still gates the artifact / pdf-template / image-search families, which is why it stays a per-site row. Capture's only env gate is the fleet-shared `PDF_TOOL_BASE_URL` + `PDF_TOOL_AGENT_RUN_TOKEN` pair (family `pdf_bridge`). |
| `TRACKING_PROJECT_ID`      | per-site             | The client's partition in the tracking owner-DB (resolver `trk_<shortId>` convention).         |
| `TRACKING_SALT`            | per-site             | Hashing salt; **must differ per site** for cross-client privacy isolation.                      |
| `TRACKING_SINK_URL`        | fleet-shared | Inherited automatically from the operator provisioning env (`TRACKING_SINK_URL`) and installed as a Functions-only secret. One shared owner DB is allowed with `TRACKING_PROJECT_ID` as the partition; per-site override remains an escape hatch. |
| `TRACKING_SINK_TOKEN`      | fleet-shared | Inherited automatically from the operator provisioning env (`TRACKING_SINK_TOKEN`) and installed as a Functions-only secret; pairs with `TRACKING_SINK_URL`. |

| `STRIPE_SECRET_KEY`          | per-site, optional   | Shop module (only if the client sells); each client's own Stripe account.                |

| `STRIPE_WEBHOOK_SECRET`      | per-site, optional   | Shop webhook signing secret.                                                             |

| `PURCHASE_TOKEN_SECRET`      | per-site, optional   | HMAC secret (`packages/core/server/lib/purchase-tokens.ts`) that signs the expiring, bearer download token gating digital-goods delivery — `get-purchase`, `order_reissue`, `stripe-webhook`, and `claim-free` (free-product claims too, not just paid Stripe orders) all read it via the same `purchaseTokenSecret()` predicate. **Site-identity overrides (transitional):** the resolver
(`src/lib/site-identity.ts`) also reads `SITE_TAXONOMY_ID`,
`SITE_TRACKING_PROJECT_ID`, `MCP_SERVER_NAME`, `MCP_SERVER_DIAGNOSTIC_NAME`,
`SITE_ASSET_HOST`, `SITE_ASSET_FOLDER`, `PDF_TOOL_PROJECT_ID` as per-site
overrides. These are **transitional**: T11.5 moves the source of truth into
`sites/<client>/site.config.*`, after which `create-site` writes the config
file and these env overrides are only an escape hatch. `create-site` should
prefer the config file and surface these names in the checklist for parity.

## Deliver

A rehearsable provisioning path: `create-site --dry-run` fully plans a client; with a token it executes the automatable half.

## Non-goals

- No DNS automation. No real second site created in this task (T11.11 does that with credentials).

## Acceptance criteria

- Unit tests over scaffold output (config validates, seeds parse, ids are `<client>`-scoped); dry-run output committed as a fixture; no secret material in any artifact.
- Committed `T11.7: …`; no PR.
