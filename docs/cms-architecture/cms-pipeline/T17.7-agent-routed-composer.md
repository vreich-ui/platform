## Context

Today's composer is a bare textarea that always does the same thing. The
concept turns it into the point where a human hands work to the assigned
article agent — three intents, one field. Everything it routes to already
exists (object-scoped chats, the roster, the approval path); this task wires
them to the margin.

## Scope

- **Three modes**, selected by a compact control on the composer, per spec
  §6.1:
  1. **Note** — `marginalia_create` / `marginalia_reply` via
     `resolveComposerAction`. Exactly today's behaviour, and the default.
  2. **Ask for a change** — the same thread write **first**, then
     `createObjectChat(objectType, objectId)` +
     `sendChatMessage(chatId, text, focus)` with `focus` naming the anchor
     (`sectionId` / `nodeId` / `field` / `selectedText`).
  3. **Ask a question** — same two writes, marked read-only in intent.
- **Order and failure semantics:** the thread write is what the UI confirms
  on. A failed chat start is reported as a system line **inside the thread**;
  a comment is never lost because an agent was unavailable.
- **Agent identity, resolved without creating anything** (spec §6.3):
  `listProfiles(getToken)` → `assignments.objects[objectId] ??
  assignments.types[objectType] ?? assignments.site_default`, matched into
  `profiles` for `name` and `avatar_artifact`. Header renders
  `→ {profile.name} · via CMS Agent`. **Rendering a header must not create a
  chat object.** With no resolvable profile, the header degrades to
  `via CMS Agent` and modes 2 and 3 are **disabled with a stated reason**,
  never routed nowhere.
- **The agent's answer returns to the thread** (spec §6.2): the run's final
  `assistant_text` is posted as a `marginalia_reply` authored by the agent
  principal. For a change request the reply also names the resulting draft
  revision, so the thread reads as *asked → happened*. Reuse the existing
  approval path untouched — a tool call that needs approval still surfaces
  through `tool_approval_required` / `approveTool`.
- **Read-only intent — new server work, called out as such** (spec §6.5):
  nothing today makes a single run read-only. `tool_autonomy_overrides` is
  profile-scoped, not message-scoped. Add an optional per-message intent to
  the `send` action that maps write-capable tools to `ask` **for that run
  only**; default unchanged. Design it as a narrow, additive field on the
  existing request union — not a new endpoint, not a new profile.
- **`✎ edit directly`** in the card header: leaves the agent route and enters
  T17.8's inline editor on the anchored block. It is a shortcut, not a second
  edit path. If T17.8 has not landed in the runner's history for this branch,
  wire it to `openPanel(target, region, 'edit')` and say so in the commit.
- **Unit tests (`node:test`):** mode→actions mapping (which writes fire, in
  what order, for each of the three modes); the profile-resolution chain
  (object → type → site default → none) from an `AgentAssignmentsView`
  fixture; the focus-payload builder from an anchor; and the degraded
  no-profile state.

## Acceptance criteria

- Against the PDF: the thread card header names the assigned agent and reads
  `· via CMS Agent`; the composer offers note / change / question; the
  placeholder matches the concept's intent.
- A **note** behaves exactly as it does today (proven by the existing
  `resolveComposerAction` tests still passing unmodified).
- A **change request** produces both a thread comment and an object-scoped
  agent run whose proposal arrives on the existing approval path; the answer
  lands back in the thread as an agent-authored reply.
- A **question** produces a run that does not silently patch anything.
- No profile assigned → header degrades, modes 2/3 disabled with a reason, no
  chat object created by merely rendering.
- `npm run check` and `npm test` green. Committed `T17.7: …`; no PR.

## Non-goals

No new agent, no new profile, no roster UI changes. No streaming chat
transcript in the margin — the thread shows the answer, the full run stays in
`/admin/agents`. No change to tool-approval policy or autonomy defaults
beyond the per-message intent above. No notifications (T17.10).
